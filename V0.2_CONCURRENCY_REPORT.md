## Busy-thread mechanisms

| Mechanism | Result | What was shown |
|---|---|---|
| `turn/start.toolOutput` | PASS | Request accepted on a disposable active turn and the turn completed. |
| `turn/steer` | PASS | Request accepted on a disposable active turn and the turn completed. |
| `thread/inject_items` | PASS | Request accepted on a disposable active turn and the turn completed. |
| `thread/queue/add` | PASS | Submission was added, listed and explicitly deleted on a disposable active turn. |
| `thread/resume + turn/start` | PARTIAL | Resume before a rollout was rejected with the installed server's structured error. |
| `codex exec resume` | UNKNOWN | No verified mapping from an App Server disposable thread to a Desktop CLI session. |

Every candidate mechanism has `safe_completion_delivery=UNKNOWN`. The probe
did not claim message order, Desktop UI visibility, receiver acknowledgement,
or protection against duplicate turns from protocol acceptance alone. The
aggregate `busy_thread_delivery` is therefore `PARTIAL` and remains blocked
from production use.

## Idle-check race

The controller attempted the sequence `read idle -> external turn start` with
separate App Server clients. The probe could not establish a stable shared
thread/control target: the controller read state was `notLoaded` and its
follow-up turn request received `thread not found`. The result is `UNKNOWN`,
not proof of safety or proof of a race-free check. An idle observation has no
reservation semantics and cannot authorize automatic delivery.

## Interrupt races

The live harness attempted `child_start`, `threshold_before`,
`threshold_after`, `command_end` and `simultaneous`. Each run was `UNKNOWN`
because the model completed without invoking the requested terminal command.
The separate earlier E2E history contains one successful supervisor/child
survival run, but repeatability was not established; the aggregate handoff
gate is `PARTIAL`.

## Durable completion races

All six local cases passed in each of 10 repetitions, for 60 case executions:

- J1 rejected a second delivery without an acknowledgement or explicit duplicate permission.
- J2 recovered both before-rename and after-rename controller crashes.
- J3 recovered an ACK write crash after rename without losing the ACK.
- J4 required an explicit duplicate-aware retry and preserved the event id.
- J5 allowed only one concurrent delivery claimant; the competing process observed the claim.

These cases use the local manual-file outbox and do not create real Codex
messages or turns. They support at-least-once-compatible recovery with an
explicit duplicate acknowledgement. Exactly-once delivery is not claimed.
