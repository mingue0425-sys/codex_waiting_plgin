The stable and experimental generated schema files were produced by the
installed binary for each run. Experimental presence is recorded separately
from runtime acceptance and from safe product behavior.

## Identity experiments

The CLI-to-CLI experiment created a unique marker, then `codex exec resume`
restored it in conversation history. This proves a usable explicit CLI
session fallback. It does not prove Desktop UI visibility, current-turn
ownership, cwd restoration, model configuration restoration, tool state
restoration, sandbox restoration or approval restoration.

The App Server could list and read stored local threads, and a disposable
`thread/start` followed by `thread/read` retained its thread id. This proves
storage visibility for that App Server instance. It does not prove that the
external process controls the runtime used by the user's Desktop window.
Desktop-to-CLI and Desktop-to-App-Server same-thread/UI experiments remain
`UNKNOWN`; no Desktop target was mutated.

## Error behavior

`thread/resume` on a newly created thread without a completed rollout returned
the structured error `no rollout found for thread id ...`. A selected active
user thread rejected resume with `already has an active writer`; the probe
records that as an observed precondition and does not retry it. The active
thread was never used for completion delivery.

API acceptance is recorded as a protocol fact. It is not promoted to a safe
completion guarantee, a Desktop UI update, or exactly-once behavior.
