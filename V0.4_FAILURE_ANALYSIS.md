# Codex Snooze v0.4 failure analysis

v0.4 proves the explicit handoff mechanics on a Snooze-owned App Server, but
the release gates correctly remain closed. The aggregate is
[results/v0.4/capabilities.md](results/v0.4/capabilities.md).

## Blocking failures

### Sandbox and approval parity

The installed `command/exec` implementation accepted a command with an
explicit workspace-only policy and still allowed a temporary sibling write.
No approval request was observed for that write. This produces
`SANDBOX_PARITY=FAIL` and `APPROVAL_PARITY=FAIL`, and the report marks
`DISABLED_SECURITY_GATE`. The code retains the ordinary server path and policy
object so the behavior is visible and testable; it does not compensate by
running a local command outside the server or by enabling a bypass flag.

### Desktop attach

The Desktop-owned App Server has no supported external reconnect surface in the
measured environment. `DESKTOP_ATTACH=FAIL` remains fixed, so v0.4 only claims
same-thread continuation for a thread created and owned by Snooze.

### Automatic PreToolUse interception

The hook remains transparent. v0.4 uses a named dynamic tool selected by the
model and does not rewrite ordinary terminal calls. `AUTO_PRETOOL_INTERCEPTION`
is therefore `FAIL` by design and no automatic interception is enabled.

## Non-blocking limitations

- Completion routing is at-least-once-compatible. The installed protocol does
  not expose the idempotency key needed for an exactly-once claim.
- The native process/spawn backend passes exit and logging checks but has no
  demonstrated Codex sandbox, so it remains experimental only.
- Token telemetry was not available in the handoff wait interval and token
  savings are not claimed.
- The normal security comparator did not exercise its fixture in the latest
  run. The owned-side sibling write still independently establishes the
  failed gate.

## Corrective acceptance conditions

The automatic path can be reconsidered only after an owned command/exec probe
denies the sibling write under the same workspace policy, records the expected
approval interaction for a command requiring approval, and repeats the result
across the supported backend. Desktop attach and PreToolUse work would require
separate supported integration surfaces; neither is inferred from the owned
thread results.
