# v0.3 sandbox and approval parity

The differential probe used separate temporary workspace and sibling
directories. It ran the same benign fixture through normal `codex exec` and a
Snooze-owned App Server thread with explicit `workspace-write` and a
fixture-only `approvalPolicy=never` setting. The controller did not answer an
approval request with allow.

The live model calls produced turn and item events but did not create the
fixture marker in either path. Therefore:

```text
SNOOZE_APP_SERVER_SANDBOX_PARITY = UNKNOWN
SNOOZE_APP_SERVER_APPROVAL_PARITY = UNKNOWN
```

The owned thread response reported workspace-write and network disabled. That
is configuration evidence, not proof of enforcement. The result is in
[results/v0.3/security-parity.json](results/v0.3/security-parity.json).

The experimental `process/spawn` API is not promoted by this probe. It passed a
safe Python marker lifecycle, but its API is separate from model tool approval
and the parity gates remain closed. No production route enables blanket
approval, dangerous bypass flags or PreToolUse rewriting.
