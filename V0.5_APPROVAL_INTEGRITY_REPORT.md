# Codex Snooze v0.5 approval integrity report

The installed schema defines the server request
`item/commandExecution/requestApproval` and decisions including `accept`,
`acceptForSession`, `decline` and `cancel`. The probe used
`approval_policy=on-request` in disposable threads.

The DENY cases returned an explicit `decline` only for a matching approval
request. The ALLOW case would accept only a request whose payload contained
the exact benign fixture fragment; every other server request was rejected.
This is a scoped test handler, not a production allow policy.

In the live cases the model's normal command item was visible, but no approval
request arrived and the local fixture side effects were absent. The result is
therefore:

```text
NATIVE APPROVAL PARITY = UNKNOWN
approval lifecycle = not observed for the local fixture
automatic approval = disabled
```

The separate allow and deny records are retained in
[results/v0.5/approval-parity.json](results/v0.5/approval-parity.json). A
command hash is recorded as command-integrity evidence only. It does not prove
that a user approved the command's semantic action.

The v0.4 controller-level reference remains an approval failure because its
sibling write occurred without an approval request. The v0.5 work does not
repair that path by removing approvals or enabling `approval_policy=never`.
