# Codex Snooze v0.6 security parity

The same disposable workspace/sibling fixture semantics were requested from
both candidates through normal Codex thread turns:

```text
workspace write
sibling write
sibling read
```

The approval recorder used `on-request` and returned a decision only for a
matching benign fixture fragment. It never blanket-approved a request and did
not modify global Codex configuration.

## Measured result

| Backend | Normal command event | Fixture side effect | Approval request | Sandbox | Approval |
|---|---:|---:|---:|---|---|
| `THREAD_NATIVE_TERMINAL` | observed | absent | absent | **UNKNOWN** | **UNKNOWN** |
| `SANDBOX_DESCENDANT_SUPERVISOR` | observed | absent | absent | **UNKNOWN** | **UNKNOWN** |
| `CONTROLLER_COMMAND_EXEC` | v0.4 reference | sibling write reproduced | absent | **FAIL** | **FAIL** |

The model reported successful command execution and the App Server emitted a
normal command item, but the probe process could not observe the temporary
fixture side effects. That execution-namespace mismatch prevents a parity
claim. The absent approval request also prevents an approval PASS claim.

Backend B's supervisor fixture was created as a child of the command requested
from the normal thread. The controller did not start the supervisor or its
child. Since the fixture side effects and descendant process records were
absent, this does not establish sandbox inheritance or approval integrity.

The negative control remains immutable. Its sibling-write result is evidence
that controller-level `command/exec` is unsafe for production selection; it is
not evidence that A or B passed. See
[results/v0.6/sandbox-parity.json](results/v0.6/sandbox-parity.json) and
[results/v0.6/approval-parity.json](results/v0.6/approval-parity.json).
