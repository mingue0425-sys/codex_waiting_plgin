# Codex Snooze v0.3 App Server architecture

v0.3 adds an explicit Snooze-owned control plane alongside the existing
supervisor/data plane. `codex-snooze agent` starts one `codex app-server
--stdio` child, performs `initialize`, creates or resumes a Snooze-owned
thread, and keeps that JSON-RPC connection alive across requested turns.

| Component | Responsibility |
|---|---|
| `AppServerProcess` | Child ownership, handshake, partial JSONL buffering, request IDs, notifications, server requests, stderr diagnostics, lifecycle and crash state. |
| `ThreadRegistry` | Durable `owner=codex-snooze` records, App Server instance identity, cwd, policy and turn history. |
| `AgentController` | Thread creation/resume, turn start/wait, explicit continuation and event trace. |
| `CompletionRouter` | Event marker, duplicate guard, `SENT_UNCONFIRMED` and explicit ACK/retry. |
| `NativeAppServerBackend` | Opt-in experimental `process/spawn` fixture backend. |
| Existing supervisor | Detached shell/process-group execution, result integrity, logs, recovery and manual delivery. |

The App Server lifecycle is independent from thread and job state:

```text
STOPPED → STARTING → INITIALIZING → READY
                         │             │
                         └─────────────┴→ CRASHED / FAILED
CRASHED → RESTARTING → INITIALIZING
```

Stdout is parsed only as newline JSON-RPC. The reader keeps a byte buffer so a
JSON object split across multiple reads is reconstructed before parsing.
stderr is bounded diagnostics and is never treated as protocol. Unsolicited
server requests are recorded and rejected with an explicit error by default;
there is no blanket approval response.

The installed schema supports `thread/start`, `thread/resume`, `turn/start`,
`turn/completed`, `thread/tokenUsage/updated` and experimental process APIs.
The native process fixture passed for an explicit Python process. It remains an
experimental backend because sandbox and approval parity for model work are not
proven.

`codex-snooze agent --task ...` is an explicit integration surface. The
classifier and PreToolUse rewrite are deliberately absent. The existing
`submit` command continues to use the v0.1 supervisor while v0.3 safety gates
remain unproven.

Durable history, a live App Server runtime, a Desktop UI instance and a
Snooze-owned runtime are distinct objects. A successful `thread/resume` does
not imply that live tool state or Desktop UI state was restored.
