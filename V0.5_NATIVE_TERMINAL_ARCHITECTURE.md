# Codex Snooze v0.5 native terminal architecture

v0.5 separates execution authority from waiting and completion ownership.
Candidate backends A and B are allowed to observe or receive ownership only
after Codex has started the original command through its normal thread tool.
The Snooze controller does not start the candidate command.

## Backend boundaries

| Backend | Execution source | v0.5 result | Production use |
|---|---|---|---|
| `THREAD_NATIVE_TERMINAL` | normal thread `commandExecution` item | **UNKNOWN** | disabled |
| `SANDBOX_DESCENDANT_SUPERVISOR` | supervisor launched inside a normal sandboxed command | **UNKNOWN** | disabled |
| `CONTROLLER_COMMAND_EXEC` | Snooze controller `command/exec` request | **FAIL** | regression/reference only |

The selector in `snooze_controller/v05_backend.py` requires PASS for command
integrity, sandbox parity, approval parity, ten-second handoff, process
survival, model inactivity and same-thread continuation. `UNKNOWN` or
`PARTIAL` selects `CLI_RESUME_FALLBACK`.

## Installed runtime facts

The installed runtime is `codex-cli 0.153.4`. The regenerated schema is in
[results/v0.5/runtime-schema/](results/v0.5/runtime-schema/) and its bounded
summary is [results/v0.5/native-terminal-schema.json](results/v0.5/native-terminal-schema.json).

The schema exposes normal `commandExecution` item lifecycle events,
`item/commandExecution/outputDelta`, approval requests, `turn/interrupt`, and
the experimental `thread/backgroundTerminals/list`, `terminate` and `clean`
methods. Background terminal records can contain `command`, `cwd`, `itemId`,
`processId` and optional `osPid`.

The schema also exposes two separate standalone paths. Streaming
`command/exec` identifiers and output are connection-scoped; the schema says
the server terminates that process when its originating connection closes.
`process/spawn` returns a connection-scoped handle but explicitly describes
host execution without a Codex sandbox. `thread/shellCommand` explicitly runs
unsandboxed with full access. None of those paths is a v0.5 production
candidate.

The local JSONL event stream and `thread/tokenUsage/updated` notifications are
available for observation, and the schema contains a `traceparent` field. No
external OpenTelemetry exporter or collector was configured for these probes.

## Ownership state

The durable ledger uses:

```text
FOREGROUND
  -> HANDOFF_PENDING
  -> NATIVE_BACKGROUND or SUPERVISOR_BACKGROUND
  -> COMPLETING
  -> COMPLETED
```

Each transfer is a file-lock-protected compare-and-swap. A job record has one
backend owner and cannot change backend during transfer. The 100-iteration
race artifact reports one winner and one CAS rejection per iteration; this is
an ownership invariant, not an exactly-once delivery claim.

## Safety gate

The v0.5 implementation intentionally leaves production automation disabled.
