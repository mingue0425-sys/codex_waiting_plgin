# Codex Snooze v0.4 security parity report

The security gate failed and automatic handoff production use remains disabled.
The full machine-readable result is
[results/v0.4/security-parity.json](results/v0.4/security-parity.json).

## Observed boundary failure

The owned App Server sent `command/exec` a `workspaceWrite` policy with the
owned workspace as its only `writableRoots` entry and `networkAccess=false`.
The benign fixture wrote both its intended file inside the workspace and a
second file in a temporary sibling directory. The response reported success
for both writes:

```text
inside.ok = true
outside.ok = true
```

The result records `owned_path_wider_than_workspace=true`,
`SANDBOX_PARITY=FAIL` and `APPROVAL_PARITY=FAIL`. No approval request was
observed and no explicit approval rejection was sent before the sibling write,
so the approval behavior cannot be treated as equivalent to the expected
normal policy.

The normal `codex exec` comparison completed its turn but did not exercise the
fixture in this run (`normal_fixture_exercised=false`); that makes the normal
side inconclusive, while the owned-side boundary violation is sufficient to
fail parity. The benign environment marker was observed in the owned process;
no secret was used.

## Related backend result

The native process/spawn differential probe preserved exit status and logging,
but the installed schema describes host execution without a Codex sandbox.
It is therefore `NATIVE_BACKEND=PARTIAL`, `native_sandbox=FAIL` and
`EXPERIMENTAL_ONLY`.

## Safety decision

The dynamic tool requires a bound Snooze-owned App Server in production and
passes the policy object through the server. It does not fall back to a local
subprocess automatically, add a blanket approval handler or enable a
dangerous bypass flag. The measured server behavior is still unsafe for an
automatic production gate, so:

- `SANDBOX_PARITY=FAIL`
- `APPROVAL_PARITY=FAIL`
- `production_automation=DISABLED_SECURITY_GATE`
- selected production path remains `CLI_RESUME_FALLBACK`

Promotion requires repeating the boundary fixture with a sibling write denied
and an approval request handled according to the normal policy. The acceptance
condition is a measured parity result, not the presence of a policy field in a
JSON-RPC request.
