# Codex Snooze v0.4 handoff architecture

v0.4 adds an explicit handoff path for a Snooze-owned App Server thread. The
model must select the named `codex_snooze_handoff` dynamic tool. The path is
experimental and has no Desktop attach or automatic PreToolUse interception.

## Control flow

```text
model turn
  |
  | item/tool/call: codex_snooze_handoff
  v
owned App Server request handler
  |
  | validate argv, cwd and threshold
  | nested command/exec with workspaceWrite policy
  v
codex-snooze handoff
  |
  | create JobSpec and detached supervisor
  | wait only until threshold_seconds
  | atomically write handoff.json
  v
DETACHED marker -> HandoffController
  |
  | record thread/turn/job mapping
  | interrupt the current turn
  | wait on result.json and delivery state
  v
same owned thread -> explicit continuation turn
```

The dynamic tool is deliberately narrower than a general server-request
handler. It accepts only `item/tool/call` for its exact tool name. Approval
requests and unrelated server requests return no tool response, allowing
`AppServerProcess` to send its explicit rejection. The handler runs on a
background thread because it issues a nested `command/exec` request; handling
it on the JSONL reader thread would prevent the nested response from being
read.

The nested request uses the ordinary App Server command path and sends the
explicit policy object:

```json
{
  "type": "workspaceWrite",
  "writableRoots": ["<owned-workspace>"]
}
```

The v0.4 security probe shows that the installed implementation did not honor
that boundary for a temporary sibling path. That finding is a release gate,
not a reason to add a local subprocess bypass. The local fallback exists only
when a unit test explicitly opts into `allow_local_fallback=True`; production
construction requires a bound `AppServerProcess`.

## Durable state and ownership

The CLI writes a structured `handoff.json` marker before returning the
foreground turn. The marker contains `job_id`, supervisor identity,
`threshold_seconds`, event version and `state=DETACHED`. The supervisor owns
the child process, writes bounded logs, computes the exit state and stores the
completion event. Git fingerprints distinguish `COMPLETED` from
`COMPLETED_STALE`.

`ThreadRegistry` records only threads created by Snooze and binds each handoff
to one thread, turn, item and job. `CompletionRouter` persists its state before
starting a continuation. A duplicate claim for an in-flight event is rejected;
`SENT_UNCONFIRMED` still requires explicit duplicate permission. The protocol
does not expose an idempotency key, so v0.4 claims at-least-once-compatible
routing and does not claim exactly-once delivery.

## Turn and failure boundaries

The controller interrupts only the turn that produced the marker. The job is
already a separate supervisor process and continues after the turn closes. The
controller waits without issuing model turns, then starts a new continuation
on the same owned thread after the result is durable.

The App Server can crash after the marker without killing the job. A controller
checkpoint can likewise be recovered by a new controller. Both paths were
exercised in v0.4. These recovery results preserve the same at-least-once
delivery limitation.
